## ✏ Ваша задача

За отведённое время вам предлагается:

### 📚 1. Создать новую сущность `Event`
Добавьте новую сущность `Event` со следующими полями:  
⦁ `id` — уникальный идентификатор события  
⦁ `venue` — связь события с уже существующей сущностью `Venue` (Many-to-Many).  
⦁ `name` — название события (`String`, NOT NULL)  
⦁ `startTime` — дата и время начала события (`LocalDateTime`, NOT NULL)  
⦁ `endTime` — дата и время окончания события (`LocalDateTime`, NOT NULL)

**Добавьте в GraphQL-схему:**  
⦁ Возможность запросить список событий с информацией о площадке (`Venue`).  
⦁ Возможность запросить список площадок (`Venue`) с информацией о последних событиях (`Events`) на этой площадке.  
⦁ Возможность создать новое событие, указав `venue-referenceId`, `name`, `startTime` и `endTime` через `mutation`.

## ✏ Комментарии по коду
* Связь many-to-many кажется избыточной, плюс возможно стоит посмотреть в сторону Spring Jdbc, так как Hibernate в небольших приложениях скорее только усложняет реализацию
* Миграции БД. Нет версионирования, не вижу надобности в повторном выполнении скрипта `R__Venue_table.sql`. При измененях структуры таблицы лучше придерживаться версионирования
* Миграции БД. Нет информации по автору и задаче, в рамках которой были добавлены скрипты. Нет роллбек скриптов
* В сущностях не рекомендуется использовать аннотацию `@Data`, так как могут быть проблемы с производительностью при использовании методов `toString(), hashCode(), equals()`. Исправлено в новой сущности.
* Методы `events`, `venueWithLatestEvents`: будет лучше если добавить пагинацию в эти методы.
* Метод `saveEvent`: если создавать событие только по наличию venue-referenceId, name, startTime и endTime, в таком случа нельзя добиться идемпотентности запроса.
* Баг. Не добавлены репозитории для зависимостей
* Баг. Метод `getVenueById` (`VenuePgDao:27`) всегда возвращает пустой `Optional`
* Баг. Должна быть аннотация `@DgsMutation` (`VenueDgsMutation:17`)
* Баг. Метод `save` (`VenueDomainService:19`) работает только для обновления, а не для создания.
* `Optional.of()` по умолчанию кидает исключение `NullPointerException`, я бы предложил использовать кастомное исключение и стат. конструктор `Optional.ofNullable()`
* В классе `ShutdownAfterMigrationCallback` используется `System.exit(0)` после миграции. Не встречал такую практику и выглядит не очень, возможно стоило бы посмотреть в сторону разных профилей.
